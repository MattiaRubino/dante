## 4. Materialization classification vocabulary

AI-03C refines the earlier classification into the following physical state classes.

### M0 — Existing canonical Domain/PostgreSQL state

Durable semantic truth/history already owned by accepted Domain/Logical/PostgreSQL structures.

Examples:

```text
Person / Event / Plan / Observation identity
accepted material state/history
Decision / Consent / Visibility / policy/governance semantics where materialized
accepted user-owned facts/preferences represented by their proper Domain owner
material-state retirement / anti-resurrection control
```

AI must not duplicate M0 into a generic memory store.

### M1 — Transient runtime state

Necessary only during one bounded request/step/Run and reconstructable without durable survival.

Default:

```text
process memory / bounded runtime object
NO durable write
```

### M2 — Durable execution runtime state

State that must survive process failure/suspension/retry because the **execution** is durable.

Physical class:

```text
Restate target where Class-B durable execution is justified
```

This is deliberately distinct from canonical PostgreSQL and from derived memory.

### M3 — Recomputable derived state

Derived information whose loss is acceptable because it can be reconstructed from currently eligible source basis.

Default:

```text
NO durability guarantee required
rebuild on demand/background
```

### M4 — Bounded durable derived state

Derived state whose survival is justified by a measured continuity/latency/cost/reproducibility need and whose source basis/lifecycle can be governed.

This class is exceptional rather than the default.

### M5 — Provider-owned optimization state

Provider thread IDs, native memory, opaque continuation, provider caches and similar state.

Rules:

```text
replaceable
compartmented
current-use eligible
never canonical authority
```

### M6 — Retrieval representation / index

Search representations such as:

```text
FTS vectors/indexes
trigram indexes
chunk/span representation
embedding vectors
ANN indexes
hierarchical retrieval summaries
```

They remain derived and source-linked even when durable for performance.

### M7 — Execution / audit / reconciliation evidence

Minimal durable evidence required to reconstruct consequential work/effects, ambiguity or reconciliation obligations.

This is not user memory and not a full prompt archive.

### M8 — Object bytes / artifact representation storage

Raw reusable object bytes belonging to a legitimate `ContentArtifact` or equivalent accepted content lifecycle.

Physical target remains object storage such as R2 when activated; canonical identity/material semantics remain PostgreSQL-owned.

### M9 — NOT JUSTIFIED TO STORE

State for which no present durable requirement exists.

This is a first-class accepted result, not missing implementation.

## 6. Primary materialization rule — persist the obligation, not the blob

A recurring failure mode in AI systems is to retain every intermediate payload because some future step might need continuity.

DANTE adopts the narrower rule:

> **Persist the minimum state needed to preserve a real obligation, reconstruct consequential execution or satisfy a proven continuity requirement; do not persist the entire transient context merely because it preceded the obligation.**

Example:

```text
model/context/tool work
→ external effect outcome becomes ambiguous
→ reconciliation obligation exists
```

The durable requirement is the reconciliation/effect evidence required to resolve that ambiguity.

It does **not** automatically require permanent survival of:

```text
full ConsumerContext
all ContextFragments
all retrieved document text
full model scratch state
entire chat transcript
all intermediate candidates
```

This rule reduces privacy exposure, retention burden, recovery complexity and accidental alternate sources of truth.

## 7. Adaptive/derived memory materialization

### 7.1 Derived hypothesis defaults to recomputation

The accepted Domain `Criterion / Evaluation` semantics already support contextual derived assessment that may be transient/recalculated or historically materialized only where consequence/reproducibility warrants it.

Therefore an AI-derived pattern such as:

```text
"recent evidence suggests the user often chooses late sessions"
```

does not justify a generic `ai_memory` row by itself.

Preferred default:

```text
eligible canonical/history basis
→ bounded Evaluation / derived assessment
→ use under current InformationNeed/purpose
→ discard / recompute later
```

A bounded durable derivative is admitted only when all of the following are justified:

```text
repeated recomputation has material cost/latency
or continuity itself is a product requirement
+
source basis can be represented truthfully
+
currentness/supersession can be revalidated
+
retention/future reuse is eligible
+
user control semantics remain possible
+
no canonical Domain owner is the more truthful home
```

### 7.2 Canonical promotion

When the user explicitly confirms a meaning that belongs in canonical application state:

```text
derived candidate
→ Proposal/Decision/governed change as applicable
→ proper Domain owner/PostgreSQL
```

After successful promotion, the materially equivalent noncanonical derivative must not remain an independent authority or independent corroboration, preserving B35.

### 7.3 User controls are not disposable derived state

A materially durable instruction such as:

```text
"do not infer/reuse this conclusion again"
```

is not safely stored inside the derivative it governs.

Otherwise deleting/rebuilding the derivative can delete the control and allow inference resurrection.

The applicable durable control belongs to accepted governance semantics according to its real meaning, for example:

```text
Decision
Conditional Policy
Consent
Visibility
other specific accepted governance owner
```

not a generic `ai_memory_permission` table.

Binding:

```text
CONTROL-PLANE DURABILITY
!= DERIVED-PLANE DURABILITY
```

Derived state may be sacrificial. Applicable user governance cannot be made sacrificial merely because the governed derivative is rebuildable.

## 9. Durable execution state and Restate boundary

### 9.1 New physical class: Durable Execution Runtime State

AI-03C explicitly recognizes:

```text
DURABLE EXECUTION RUNTIME STATE
```

as a physical class distinct from:

```text
canonical PostgreSQL state
recomputable derived memory
provider state
retrieval indexes
```

The accepted Physical target for Class-B durable execution is Restate.

This avoids the shortcut:

```text
long-running Run exists
→ therefore create dante.run / dante.run_step tables
```

Ordinary work stays transient. Only genuine durable execution earns M2.

### 9.2 Journal/checkpoint privacy

Durable runtime technology can journal/retain input, output, state and operation results. Therefore:

```text
DURABLE JOURNAL
!= PRIVACY-FREE RUNTIME
```

DANTE must minimize what crosses that persistence boundary.

Default forbidden convenience payloads include:

```text
full ConsumerContext
full private prompt
raw sensitive document corpus
entire chat transcript
unbounded tool outputs
privileged credentials
```

Prefer:

```text
stable/bounded refs
minimal typed DTOs
operation/effect identifiers
current expected-state bindings
small receipts/digests
minimum checkpoint data required to resume safely
```

When safe and practical, reread current canonical/source state after resume instead of persisting a private duplicate.

The existing Physical post-selection obligations PSV-27, PSV-28A and PSV-28B remain UNEXECUTED direct proof obligations; AI-03C does not relabel them PASS.

### 9.3 Recovery fence between canonical and durable runtime

A destructive restore can produce mismatched timelines:

```text
PostgreSQL restored to B0
Restate/runtime still contains work derived from B2
```

or the reverse.

Therefore:

```text
RUNTIME RECOVERY
!= CANONICAL RECOVERY
```

Binding rule:

> **Restored durable runtime/provider/derived state must not resume consequential work ahead of canonical PostgreSQL recovery/reconciliation readiness.**

Before consequential resume:

```text
canonical recovery/serving fence passes
→ reread current source/canonical state
→ re-evaluate current AuthZ
→ re-evaluate Consent / Visibility / represented-party scope
→ re-evaluate Work Supersession / cancellation
→ re-evaluate expected MaterialState/basis
→ continue / reject / reconcile
```

This is a recovery/serving gate, not a second authority.

A durable derivative is not allowed to become an orphan representation.

At minimum DANTE must be able to establish:

```text
source identity/location
source reality class
source version/material state/revision basis where semantically valid
transformation/generation identity
purpose/security/retention scope where material
created/derived time
current lifecycle/eligibility state
```

Where the source has a real `MaterialStateRef`, use it.

Where it does not:

```text
DO NOT INVENT A MaterialStateRef
```

Use the truthful source revision/snapshot/digest/external-reference mechanism appropriate to that source class.

If a durable source basis cannot be established sufficiently to support currentness, correction, suppression and recovery:

```text
DO NOT PERSIST THE DERIVATIVE
```

or treat it only as ephemeral M1/M3 state.

## 11. Derived generation and cutover discipline

Durable derived representations must be generation-aware.

This applies to:

```text
embedding model / dimension / normalization / distance metric
OCR/extraction version
chunking/span algorithm
text normalization
FTS configuration/dictionary
summary/hierarchy algorithm
reranker-specific representation
```

Silent in-place reinterpretation is rejected.

Candidate migration pattern:

```text
GENERATION A serving
        ↓
build GENERATION B from currently eligible sources
        ↓
validate correctness / recall / security / resource behavior
        ↓
controlled cutover A → B
        ↓
A becomes non-serving
        ↓
bounded cleanup according to retention/recovery policy
```

Mixed generations must not silently participate as if semantically equivalent.

Generation identity is technical/derived metadata, not `MaterialStateRef` unless a real accepted semantic material-state contract independently exists.

## 12. Async invalidation and current eligibility

Background invalidation/rebuild is allowed and expected for derived retrieval state.

The accepted Physical target already supports:

```text
canonical PostgreSQL write
+
transactional outbox
→ bounded worker
→ rebuild / invalidate derivative
```

But:

```text
ASYNC CLEANUP
!= CURRENT ELIGIBILITY AUTHORITY
```

A delayed worker must not leave a redacted/retired/forbidden derivative legitimately serving merely because the physical row/index entry still exists.

Serving must remain able to enforce current eligibility from authoritative lifecycle/governance state before returning or materially using a derivative.

This directly preserves the existing stale-index/deletion propagation obligations in SC-020 and SC-021.

## 13. Derived recovery / anti-resurrection

Recomputable retrieval state is intentionally sacrificial.

Preferred restore semantics:

```text
restore canonical PostgreSQL candidate
→ semantic reconciliation / recovery readiness
→ restored derived bytes are NOT serving-eligible by default
→ verify source lifecycle / suppression / generation / basis
→ discard + rebuild
   OR explicitly reconcile
→ only then mark eligible for serving
```

Binding:

```text
RESTORED DERIVED BYTES
!= RESTORED ELIGIBILITY
```

This includes where applicable:

```text
OCR/extraction
chunks
summaries
embeddings
FTS/vector/search representation
retrieval cache
provider-side persisted retrieval state
adaptive/operational derivatives
```

`material_state_retirement` and Recovery suppression semantics remain stronger than any recovered stale derivative.

Rejected shortcut:

## 15. Semantic/vector retrieval posture

### 15.1 Vector search is optional

The presence of pgvector does not imply an embedding table or ANN index.

Candidate progression:

```text
PHASE 0
no vector path until a real retrieval consumer exists

PHASE 1
admit a source-linked embedding representation only if semantic retrieval adds value

PHASE 2
establish an EXACT nearest-neighbor baseline inside the currently eligible universe

PHASE 3
benchmark exact correctness/latency/resource behavior

PHASE 4
only when exact becomes insufficient, compare ANN options

PHASE 5
activate HNSW / IVFFlat only after direct recall + security + recovery + resource proof
```

### 15.2 Exact-before-ANN rule

pgvector exact search is the correctness baseline. ANN is an optimization that trades recall for performance.

Binding:

```text
ANN IS AN OPTIMIZATION
NOT A RETRIEVAL PREREQUISITE
```

Approximate Top-K must never satisfy a complete-required InformationNeed merely because it is fast.

### 15.3 Filtering/non-interference is part of ANN acceptance

The Physical benchmark already requires correctness/recall **after** real scope/Visibility filtering and includes long-tail candidate sets where approximate recall can degrade.

Therefore ANN acceptance must measure at minimum:

```text
exact-reference oracle
unfiltered recall@k
filtered recall@k
precision@k
latency distribution
candidate counts before/after eligibility filtering
resource usage
index build/rebuild cost
non-interference across hidden/tenant/scope populations
```

SC-019 and PSV-08 remain the canonical direct obligations for this decision.

No present evidence justifies choosing HNSW or IVFFlat, parameters, embedding dimension, distance metric or specialist vector database.

## 16. Cache posture

A cache may improve latency but does not create durable semantic memory.

Default rules:

```text
CACHE HIT != CURRENT AUTHORIZATION
CACHE HIT != CURRENT SOURCE ELIGIBILITY
CACHE HIT != CURRENT DISCLOSURE PERMISSION
```

A cache entry may be discarded at any time unless a separate explicit continuity contract proves otherwise.

No Redis or dedicated cache store is justified by AI-03C at this checkpoint.
