## 1. Decision

DANTE uses one polyglot monorepo with explicit ownership by path.

The repository root is coordination space, not an application source directory.

## 2. `apps/` — deployable/runnable products

`apps/` contains software with an independent runtime/build target.

### `apps/api`

The DANTE backend modular monolith.

Owns:

- Python runtime manifest/lock;
- FastAPI composition/bootstrap;
- backend modules;
- database mappings/adapters;
- Alembic migration chain;
- backend-specific tests;
- server OCI image definition when deployment begins.

It does not own:

- web/mobile UI;
- shared TypeScript generated client;
- provider IaC;
- repository-global scripts.

### `apps/web`

The production Next.js web client.

The existing `prototypes/` material is not production web code by identity. Production adoption from a prototype requires an explicit implementation/migration scope rather than copying prototype state blindly.

### `apps/mobile`

The Expo/React Native client for Android/iOS.

Native platform directories generated by Expo/CNG are treated according to the selected Expo workflow at scaffold time; generated native output is not committed merely because a local tool produced it.

## 3. `packages/` — genuinely shared TypeScript artifacts

`packages/` is intentionally narrow.

A package exists only when at least two consumers or one durable generated-contract need justifies it.

### `packages/api-client`

Generated TypeScript API client/types from the authoritative backend OpenAPI contract.

Rules:

- generated deterministically;
- generator version locked;
- generated files marked as generated;
- no hand edits;
- CI regeneration/drift check;
- package version/contract identity traceable to backend source SHA.

### `packages/design-tokens`

Platform-neutral design tokens only: color/spacing/typographic/semantic token data that can be represented without importing React DOM or React Native behavior.

This is not a forced shared component library.

### `packages/eslint-config` / `packages/typescript-config`

Shared code-quality configuration only when multiple TS projects exist. Centralization prevents policy drift while app-specific exceptions remain explicit.

## 4. What does not go into `packages/`

Forbidden patterns:

```text
packages/shared
packages/common
packages/utils
packages/helpers
```

as generic dumping grounds.

A shared package must have a precise purpose and ownership. Duplicate code may temporarily be cheaper and safer than a premature abstraction.

Python code remains inside the modular backend until an actual independently versionable/reusable Python library exists. Engineering Foundation does not manufacture Python packages to make the tree look symmetric.

## 5. `infra/`

`infra/` owns infrastructure definitions, not application business logic.

### `infra/compose`

Local stateful-dependency topology and developer dependency profiles.

Examples when activated:

- PostgreSQL 18.4 with selected extensions;
- PgBouncer;
- local observability collector/pipeline;
- additional selected services only when their implementation boundary arrives.

Application processes are not forced into Compose for daily inner-loop development.

### `infra/iac`

Remote durable infrastructure definition.

```text
infra/iac/modules/
reusable bounded infrastructure modules

infra/iac/environments/dev/
DEV composition/inputs

infra/iac/environments/uat/
UAT composition/inputs

infra/iac/environments/prod/
PROD composition/inputs
```

Environment directories contain configuration/desired-state references, never plaintext secrets.

The exact IaC engine is selected/pinned when the first remote infrastructure is implemented. Until then the directory is a contract, not a reason to create fake Terraform/OpenTofu files.

### `infra/policies`

Machine-readable infrastructure/security policy only when a real policy-as-code mechanism exists. No placeholder policies.

## 6. `tooling/`

`tooling/` contains repository engineering utilities that support builds, validation, code generation or local workflows.

It must never become a backdoor application layer.

Allowed examples:

- deterministic OpenAPI/client generation scripts;
- repository validation scripts;
- synthetic fixture generation;
- migration/CI utility scripts;
- local bootstrap helpers.

Disallowed:

- business rules;
- canonical DANTE semantic logic;
- hidden production jobs that should live in an application/module;
- credentials.

Each non-trivial script must have an owner/purpose and deterministic inputs where practical.

## 7. Test ownership

Tests live with the software they validate.

```text
apps/api/tests/*
backend tests

apps/web/tests/*
web tests

apps/mobile/tests/*
mobile tests

apps/mobile/.maestro/*
native mobile E2E flows

/tests/system/*
true black-box tests spanning multiple deployed applications/services
```

Root `tests/` is **not** a general bucket for app unit tests.

Cross-system test fixtures are synthetic and must not contain copied production personal data.

## 8. Documentation and prototypes

### `docs/`

Remains durable project memory and engineering authority. Production code changes that alter accepted behavior/architecture update relevant documentation in the same PR.

### `prototypes/`

Remains explicitly non-production.

Rules:

- prototype code does not import production-private internals;
- production code does not depend on prototype paths;
- prototype acceptance requires deliberate migration/reimplementation into `apps/*`;
- prototype branch state cannot silently override `main` backend/architecture authority.

## 9. Root files

The root may own cross-repository coordination files such as:

```text
package.json
pnpm-workspace.yaml
pnpm-lock.yaml
turbo.json
.editorconfig
.gitignore
README.md
CONTRIBUTING.md
CHANGELOG.md
```

A root JavaScript `package.json` coordinates the TS workspace and does not redefine the Python API as an npm package.

The Python API owns its `pyproject.toml` and `uv.lock` under `apps/api/`. A root Python workspace is not introduced until more than one actual Python project needs shared resolution.

This avoids forcing a Python workspace abstraction before it has a second member.

## 10. Dependency direction by path

Allowed high-level dependency graph:

```text
apps/web -----> packages/api-client
         -----> packages/design-tokens
         -----> shared TS configs

apps/mobile --> packages/api-client
            --> packages/design-tokens
            --> shared TS configs

packages/* --X--> apps/*

apps/api is independent of packages/*

infra/* may reference deployable artifact identities
infra/* --X--> application source imports

tooling/* may invoke build/codegen interfaces
tooling/* --X--> canonical business-logic ownership

production apps --X--> prototypes/*
```

No package imports another application.

## 11. Generated-file policy

Generated artifacts fall into three classes.

### A. Generated and committed

Use when reviewability/offline consumption/reproducibility materially benefit, for example the TypeScript API client.

Requirements:

- deterministic generator;
- generator version locked;
- source input traceable;
- header/metadata marks generated output;
- CI can regenerate and prove clean diff.

### B. Generated locally/build-time and ignored

Examples:

- `.venv/`;
- `node_modules/`;
- Next/Expo build caches;
- coverage output;
- temporary OpenAPI generation files;
- local database volumes;
- test reports that are not intended as repository evidence.

### C. CI/release artifacts

Examples:

- OCI images;
- mobile binaries;
- web build artifacts;
- test reports;
- SBOM/attestations when activated.

These belong in the appropriate artifact store/GitHub artifact/release system, not as normal Git files.

## 12. Ignore policy

`.gitignore` is updated when the scaffold creates real tools. It must cover local secrets, caches, IDE/temp output, test/build products and stateful local volumes without hiding source/config files that should be reviewed.

Rules:

```text
ignore secrets
ignore machine-local state
ignore reproducible build output unless policy says commit
DO NOT ignore lockfiles
DO NOT ignore migrations
DO NOT ignore generated contract files selected for committed review
DO NOT ignore durable infrastructure definitions
```

## 13. File naming and language conventions

- repository directories: lowercase kebab-case where ecosystem conventions permit;
- Python packages/modules: lowercase snake_case;
- Python package namespace: `dante`;
- TypeScript packages: scoped package names may use a future DANTE namespace when manifests are created;
- generated files use tool-standard naming and explicit generated markers;
- environment name vocabulary is exactly `local`, `dev`, `uat`, `prod` where a generic environment identifier is needed;
- historical `lifeos` repository identifiers are not renamed opportunistically inside this workstream.

## 14. Ownership before team growth

The repository remains owner-driven. `CODEOWNERS` is not manufactured while it would name no independent ownership boundary.

When multiple maintainers exist, ownership can be added by stable application/module path. Review requirements should reflect actual independent review capacity, not ceremony.

## 15. Scaffold gate

Engineering Foundation documentation does not create the tree above.

The first production scaffold scope after foundation closure must enumerate every created path exactly and create only the directories/files backed by real manifests/configuration/code.

No empty directory exists in Git by itself and no placeholder file is added merely to make this diagram visually complete.
