# 2026-08-15 — Proposal / Request downstream dependency closure

Proposal / Request v0 resolves the reusable proposal/request ambiguity that remained implicit across Clusters 1–4 without introducing a universal interaction/message/workflow root.

Accepted current separation:

```text
Proposal
= materially specific candidate action/state/terms/rule/option/change put forward for consideration

Request
= directed bounded ask for action/information/response/Decision/participation/permission/change

Proposal != Request
Proposal / Request != Message / Notification
creation != delivery != view != Acknowledgement
Acknowledgement != positive response
Proposal != Agreement / Decision / effective state
Request != Responsibility / Participation / Authority / Consent / effective state
requested action != Actual execution
```

Cross-cluster closure consequences:

- Intention & Execution may originate or receive Proposals/Requests without treating them as Goals, Plans, Activities, Decisions or Actuals;
- Time may represent proposed/requested temporal changes without collapsing them into current Schedule;
- Observed Reality & Evidence preserves Proposal/Request provenance/history without treating a Proposal/Request as Evidence of the requested action having occurred;
- Data / Subjects preserves actual Actor, target/recipient/subject and represented-party distinctions without requiring Account identity;
- Version/material-equivalence binds consequential Proposal/Request semantics to the material target/request/proposal state concerned;
- Authority, Visibility, Representation, Acknowledgement, Decision, Agreement/Consent and Reconciliation remain independent governing/coordination semantics.
