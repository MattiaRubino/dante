# 2026-08-15 — Proposal / Request downstream amendment

Proposal / Request v0 closes the reusable candidate/ask boundary for temporal coordination without changing the accepted Schedule identity or turning Schedule into a negotiation workflow.

Canonical separation:

```text
Proposal
= materially specific candidate temporal action/state/terms for consideration

Request
= directed bounded ask for temporal action/information/response/change

Schedule
= current accepted/planned temporal state of the schedulable target

Actual
= realized temporal truth
```

Therefore:

```text
proposed time != current Schedule
requested time != current Schedule
proposal/request creation != delivery/view/Acknowledgement
Acknowledgement != positive response
Proposal != Decision / Agreement / Consent
Request != Responsibility / Participation / Authority
Proposal/Request != effective temporal change
requested execution != Actual execution
```

A temporal Proposal or Request becomes current Schedule only through the applicable bounded effect/governance semantics owned by the affected domain concept together with applicable Authority, Decision, Agreement/Consent or policy where required. Schedule owns the resulting temporal state; Proposal/Request owns the candidate/ask history.

Material-state rules:

- a materially changed temporal Proposal or Request does not silently inherit prior Acknowledgement, response, Agreement, Consent or Decision;
- a genuine counter-proposal is a distinct Proposal, not a silent mutation of the earlier candidate;
- Version/material-equivalence semantics identify which materially relevant Proposal/Request and Schedule state an act concerned;
- provider/storage revisions do not determine semantic materiality;
- withdrawal or expiry changes future Proposal/Request applicability but does not erase historical temporal coordination or automatically undo an already-effective Schedule change;
- a Request to move/cancel/split/reschedule does not itself create Responsibility, Participation, Authority or the resulting Schedule state;
- the requester, recipient, responsible actor, performer and represented party may all differ;
- Representation preserves the actual Actor and represented party where a temporal proposal/request is made on behalf of another;
- Visibility of the proposed/requested time, rationale and history remains independently governed;
- AI may generate a temporal Proposal or Request under bounded context, but AI proposal != human intention/Decision and AI capability != Authority.

Low-consequence UX may collapse conversational steps, but the domain boundary remains:

```text
proposed / requested
!= accepted current Schedule
!= Actual
```

No universal ProposalRequest root, generic Message/Interaction root, generic Acceptance root, Schedule workflow/state machine or universal Proposal/Request persistence table is introduced.
