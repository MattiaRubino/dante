```text

- DANTE consumes bounded authorized context;
```

# 4. Targeted reverse engineering triggered by Cycle B

Research was performed only for the concrete new gaps.

## 4.1 Revision-bound approvals and resource bindings

Official GitHub protected-branch documentation allows approving reviews to be dismissed as stale when new commits change the reviewed diff, and can require approval of the most recent reviewable push.

Useful pattern:

```text
approval
binds to a materially identified subject state
!= perpetual approval of every future mutation
```

Sources:

- https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches
- https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule

Google Calendar resource documentation separately shows that changing an event time can release a booked room and attempt to rebook it for the new time; that rebooking may fail. A resource manager can also remove a booking later.

Useful pattern:

```text
binding/resource acceptance
binds to a scoped request/basis
scope mutation may require revalidation/rebinding
```

Source:

- https://support.google.com/calendar/answer/16107253

DANTE does not import GitHub reviews or Calendar rooms as ontology. The evidence supports the more general invariant.

## 4.2 Evidence integrity / attestation

NIST digital-evidence guidance treats chain of custody and integrity as material concerns. It recommends documenting source/transfer and using hashes/digital signatures to help verify integrity.

Useful pattern:

```text
provenance/source history
!= integrity/attestation
!= freshness
```

Sources:

- https://www.nist.gov/publications/digital-evidence-preservation-considerations-evidence-handlers
- https://nvlpubs.nist.gov/nistpubs/ir/2022/NIST.IR.8387.pdf
- https://csrc.nist.gov/glossary/term/chain_of_custody

DANTE does not create a universal forensic-custody object. Integrity/attestation becomes an optional evidence/basis concern when consequence requires it.

## 4.3 Cancel / reverse / compensate

Stripe PaymentIntent documentation makes cancellation explicitly state-dependent; once an effect is in a different state, a different operation such as refund/reversal may be needed. Stripe separately documents idempotency as retry safety, not as semantic reversal.

AWS Saga guidance describes compensating transactions for partially completed distributed workflows.

Useful pattern:

```text
cancel before effect
!= undo
!= reverse/refund after effect
!= compensation after partial multi-step effect
!= idempotent retry
```

Sources:

- https://docs.stripe.com/api/payment_intents/cancel
- https://docs.stripe.com/api/idempotent_requests
- https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-data-persistence/saga-pattern.html

## 4.4 Supersession / correction / retraction

Crossref and NLM preserve explicit relationships between an original published record and later corrections/retractions rather than pretending the original never existed. Crossref specifically recommends separate update records for editorially significant corrections/retractions.

Useful pattern:

```text
freshness
!= validity/current reliance
superseded/retracted basis
!= deleted historical basis
```

Sources:

- https://www.crossref.org/documentation/principles-practices/best-practices/versioning/
- https://www.crossref.org/documentation/register-maintain-records/maintaining-your-metadata/registering-updates/
- https://www.nlm.nih.gov/bsd/policy/errata.html

## 4.5 Recurrence / occurrence confirmation

RFC 5545 separately models recurrence rules and exception date-times. Time-zone changes can affect the exact duration/interpretation of recurring instances.

Useful pattern:

```text
series rule
!= occurrence
!= exception to one occurrence
```

This confirms existing DANTE Domain distinctions; it does not create another substrate ownership class.

Source:

- https://datatracker.ietf.org/doc/html/rfc5545

# 5. New material concerns discovered by Cycle B

Cycle B did **not** converge immediately. Four new classes emerged.

## CG-33 — Scope/revision-bound validity of approvals, consent and bindings

### Trigger

B03, B04, B10, B11, B12, B13, B22, B30, B33 and BX01/BX05/BX06/BX13.

### Problem

The previous convergence model distinguished acceptance/authority/effect, but did not state strongly enough **what exact subject state an approval/consent/binding applies to**.

A materially changed subject may invalidate or require revalidation of prior approval even when the same human-readable object name remains.

### Closure

Where consequence requires it, a frontend/application projection of approval/consent/reservation/binding must preserve enough scoped basis to answer:

```text
what exact subject/configuration/revision was accepted?
under what applicable policy/eligible-actor set?
is that basis still current/applicable?
```

A change can yield:

```text
still-applicable
needs-revalidation
superseded/stale-for-binding
revoked/invalidated upstream
```

The exact authoritative policy remains application/AuthZ/Domain-owned.

Hard rejects:

```text
approval by label/name only
approval applies to future mutations automatically
World generation == approval revision
AI decides that old approval is close enough
```

This belongs primarily to L3 Coordination/Disclosure + authoritative application basis, with L6 presentation for consequential flows. It is **not** a universal Domain `Approval` object created by frontend.

---

## CG-34 — Evidence integrity / attestation distinct from provenance and freshness

### Trigger

B01, B02, B19, B36, BX02, BX16.

### Problem

The previous L2 Evidence/Basis envelope carried source/provenance/freshness/coverage, but high-consequence evidence can also require a statement about integrity or attestation.

Knowing where data came from does not prove that bytes/content remained intact; knowing that data is fresh does not establish authenticity/integrity.

### Closure

L2 Evidence/Basis may optionally carry, when material:

```text
integrity/attestation reference or status
verification basis
custody/handling trace reference
```

Rules:

```text
integrity unknown != corrupted
integrity mismatch/tamper indication != ordinary stale
custody gap != evidence automatically false
provenance != custody != integrity
```

A full custody renderer/history may be a specialist evidence presentation when required; it is not a universal work primitive.

---

## CG-35 — Cancellation, reversal and compensation after partial/real effects

### Trigger

B05, B06, B07, B23, B26, B34, B37, BX03, BX08, BX12.

### Problem

The previous L6 grammar distinguished proposal/confirmation/pending/ambiguity/reconciliation/receipt, but it was not explicit enough about what happens after a real or partial effect exists.

### Closure

L6 must preserve, when applicable:

```text
cancel request before effective execution
cancel accepted/rejected
partial effect already occurred
reverse/refund/release as a new governed operation
compensating action for a multi-step partial effect
reconciliation after ambiguous or partial completion
```

Rules:

```text
Cancel button != historical effect erased
cancel != refund
refund != generic undo
compensation != original operation failure
idempotent retry != compensation
navigation away != semantic cancellation
```

The frontend only presents typed governed states/intents; real reversibility and effect authority remain upstream.

---

## CG-36 — Basis validity / supersession / retraction distinct from freshness

### Trigger

B21, B22, B23, B32, BX04, BX10, BX14.

### Problem

`fresh` and `stale` are insufficient when a source or material state has been explicitly superseded, corrected, retracted or invalidated for current reliance.

### Closure

L2 must allow a basis-validity relation/state, when applicable, that distinguishes concepts such as:

```text
current/applicable
superseded by identified newer basis
corrected by identified update
retracted/withdrawn for current reliance
invalidated by authoritative change
```

Exact enums remain WS6/application design work; the semantic distinction is now mandatory.

Rules:

```text
retracted != deleted historical record
superseded != merely old timestamp
fresh provider copy of retracted material != valid current basis
pinned derived output != immune from basis invalidation
```

Derived DANTE or application outputs must remain traceable to the exact basis that supported them and must not continue to present themselves as current when that basis is no longer valid for current reliance.

WS6 must not begin from the old `CG-01..CG-32` map alone.

In particular:

```text
EVIDENCE / BASIS
- provenance != integrity
- freshness != validity
- current != superseded/retracted
```
