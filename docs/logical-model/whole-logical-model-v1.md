## 6. WL-H01 — Agreement terms require an owned material state

Material Agreement terms must resolve to a justified semantic owner/facet:

```text
Agreement
-> assent binds to
MaterialStateRef(justified semantic owner / facet)
```

Examples can include Proposal state, Content Artifact state, Agreement-owned dependent terms state, or another explicitly valid owner/facet. Generic `TermsRef`, `Terms` entity or ownerless `terms_id` is forbidden.

## 7. WL-H02 — Governed Operation / Effect Contract

Consequential governance cannot be reduced to free-form technical action strings. Where applicable the logical contract preserves:

```text
operation family
target semantic owner / facet
material target state
effect semantics
input/context
purpose
preconditions
governance requirements
expected-state requirement
idempotency semantics
```

Examples include cancelling an Activity, revising Schedule, exposing a bounded free/busy projection, allocating Resource, or confirming a MaterialState.

```text
HTTP route / AuthZ action / UI button
!= canonical governed effect
```

This is logical vocabulary, not a new Domain `Operation` or `Command` owner.

## 8. WL-H03 — Projection / Disclosure Surface Contract

A governed representation surface preserves where material:

```text
source owner / bounded source set
projection/facet kind
derivation/profile
source/material version
purpose/context
allowed exposure
source-disclosure boundary
recipient/governance context
```

A projection does not need persistent identity merely because it can be disclosed. `ProjectionRef` is not required.

A coarse result such as `Unavailable 18:00–20:00` may be visible while its private therapy/health cause remains hidden.

## 9. WL-H04 — absence != false

Global rule:

```text
no record
!= false
!= no
!= inactive
!= declined
!= cancelled
!= known non-realization
```

Examples:

```text
no established Actual != known non-realization
unknown Membership != non-member
unknown Availability != unavailable
no Evidence != Evidence against
not visible != nonexistent
```

Negative semantics are owner-specific; otherwise state remains unknown/unresolved.

## 10. WL-H05 — expected-state / optimistic-concurrency contract

When stale writes could destroy accepted consequential state/history:

```text
consequential mutation
+ expected MaterialStateRef or semantically equivalent precondition
-> apply only if expected state remains applicable
```

Mismatch means conflict/re-read/reconcile/retry/user resolution as appropriate, never silent overwrite.

```text
ETag / row version / MVCC token / provider revision
!= MaterialStateRef by identity
```

Such tokens may implement the check physically later.

## 11. WL-H06 — idempotency != identity

Retry-safe effects may use bounded idempotency semantics:

```text
same key + materially equivalent operation
-> may replay prior effect/result

same key + materially different operation
-> conflict/reject
```

But:

```text
IdempotencyKey
!= NativeRef
!= Goal identity
!= Request identity
!= Decision identity
!= universal Command root
```

## 12. WL-H07 — multi-owner consistency boundary

If one operation changes multiple canonical owners/relations and invariants require all-or-nothing behavior, later Physical/runtime design must supply an atomic consistency boundary.

If distributed/provider boundaries make global atomicity impossible:

```text
explicit staged state
+ partial outcome
+ reconciliation / compensation
```

The canonical model must never claim full success while a required effect is only partially established. No new universal Domain `Transaction` owner is introduced.

## 13. WL-H08 — canonical state != provider sync state

Provider apply/sync state is LR-09 integration state.

Valid example:

```text
LifeOS accepted Schedule = 16:00
provider representation  = still 15:00
sync/apply state         = failed
reconciliation           = required
```

Provider failure does not automatically roll LifeOS back; provider current value does not automatically overwrite canonical state without an explicit bounded reconciliation/precedence rule.

## 14. WL-H09 — LR-08 freshness

Derived state may be cached/materialized:

```text
Candidate Set
Effective Availability
Free Capacity
current knowledge
Effective Authority
Effective Visibility
recipient projection
```

but cached LR-08 state is not canonical truth. A consequential effect depending on derived state must either revalidate the material basis, bind to exact historical Evaluation/input state, or use a bounded consequential snapshot.

## 15. WL-H10 — retention / redaction / tombstone integrity

Privacy/deletion must not falsify historical existence. Where policy permits:

```text
historical referent existed
payload later redacted/unavailable
minimal tombstone/reference continuity retained
```

```text
redacted/unavailable != never existed
```

A deleted/retired NativeRef is never reused for another referent. Exact retention mechanics remain policy-, jurisdiction- and Physical/runtime-stage decisions.
