# B14 follow-up — Session history protection, corrections, past authoring, collision-safe geometry

**Status: PROPOSAL FOR USER ALIGNMENT / NOT YET APPROVED / NOT IMPLEMENTED**
**Date:** 2026-10-11
**Branch checked:** `feature/timeline-temporal-operational` at `20aed519` (source audit)
**Real app evidence:** user screenshot (2026-10-11): main Activity `asd` in progress and `test3` planned 10:00–10:30, real ended Session 09:49–09:51; cards appear visually overlapping and Play remains available after Stop.
**Accepted pre-existing authority:** `docs/domain/decisions/activity-session-live-timeline-v1.md`; `docs/domain/concepts/session.md`; `docs/domain/decisions/activity-intervals-and-sessions-v2.md`; B08 Session≠Schedule and B10 Actual≠Outcome.

## Verified code findings (not yet repaired)

1. `apps/web/src/features/home/ui/timeline/timeline-session-reality.ts`: after recomputing overlap lanes for projected `displayEvents`, the actual card top/height is recalculated independently from the original layout. The overlap lane algorithm uses logical interval minutes, while the rendered card uses a minimum readable height. Visual rectangles can therefore collide even when time intervals or old computed layouts are noncolliding. The correct fix uses ONE layout pass on **final displayed rectangles** (including minimum readable height, expanded mode, projected actual bounds, preserved planned data, and multiple interval scope) and regression tests for early/late/short/long overlaps at multiple zooms. No canonical Schedule timestamp mutation from layout.
2. `apps/backend/src/dante/modules/temporal/session_panel_api.py`: `ended_during_current_window` suppresses a stopped attempt only if its end overlaps the current schedule window (with just 5-minute lead). A Session started/stopped early, e.g. finished 09:51 for 10:00 planned start, can be reintroduced as Ready. `apps/web/src/features/temporal/session-subject-controls.tsx` separately exposes Play when no Session is currently open. Both must be fixed; the operational interface cannot depend on incidental proximity of historical execution times.
3. `apps/backend/src/dante/modules/temporal/activity_replan_api.py` currently vetoes ordinary replan when there is **an open Session OR a canonical Actual**; an ended Session without an Actual is not sufficient for that generic veto. There is a narrower planned-slice removal guard for recorded executions. Need one cross-command historical protection capability with PostgreSQL owner/CAS protections, not scattered frontend checks.
4. Existing manual Session recording under `SessionApplication.record_manual` requires ordered **past** instants and explicit user intent. For Events, do not silently invent a Session: the current Session API supports Activity/Occurrence subject families and B10 Event Actual is a separate canonical capability.

## Recommended product contract — must get user sign-off before schema changes

**A. Lock by real execution scope, not forever by Activity identity.** Once an Activity-associated Session starts or a manual Session is accepted, protect the **specific historical Activity interval / planned Session slice / occurrence** and its recorded facts: no ordinary drag, resize, unschedule, delete or plan time edit; block all entry points (mouse, keyboard, Inspector, API). While open/paused: disable ordinary structural/core editing on that scope. Once ended: keep it read-only in ordinary editor, with an explicit `Correggi registrazione` flow. Other untouched future intervals of the same recurring/multi-interval Activity remain independently editable; series edits must not backdate onto executed instances. Actor ownership, native identity, operation CAS and atomic checks in DB.
- **Potential unresolved design choice:** whether harmless descriptive metadata (title/notes/color) is also fully frozen on this scope or can be changed as a separately versioned metadata correction. User favors full ordinary-card lock.
- If the entire Activity is a one-off with one planned interval, the ordinary Activity card becomes locked after execution, as requested.

**B. Corrections without erasing history.** Put `Storico → Correggi registrazione` in Inspector (and link from Conclusi). Original and corrected timestamps/pause ranges remain auditable as versioned corrections with user reason, confirmed actor and operation ID; no direct SQL overwriting the original Session. A truly erroneous execution can be **retracted/invalidated with reason**, not silently erased; dependent Actual/Objective/evidence must be explicitly reviewed and not silently left authoritative. Any correction affecting planned Schedule uses its own independent planning operation and does not rewrite actual execution.

**C. Archive vs delete.** For executed work, ordinary `Elimina` becomes `Archivia` / `Rimuovi dalla vista`: hide from ordinary future planning while preserving historical Activity, Session, Actual and confirmations, with access in Conclusi/Inspector. Full erasure is not the default UI effect. For never-started work, existing legal delete/unschedule may remain governed by its own rule. Erroneous history requires explicit retraction/correction, not generic Activity delete. Include cascade/ref integrity tests and owner-only retention.

**D. Past creation/movement.** Creating/moving an Activity or Event into the past only writes a **plan**; it creates no Session, Actual, skipped, completed or Outcome. If the user wants to record what happened, offer a distinct `Registra esecuzione avvenuta` (Activity, with past start/end and optional pauses) or `Registra Evento avvenuto / non avvenuto` through B10 Event Actual/Confirmation; never create a fake Event Session. If work is past but not evidenced, preserve `non verificato` (and only a governed optional review). A live Play is about execution **now**, not about backdating a run. Existing recorded scopes remain locked when an Event/Activity is subsequently edited or moved.

**E. Stop lifecycle and cards.** Main/child Stop atomically ends the right open Session identities and cascades according to approved current rules. The **same concluded attempt** must never be re-enabled through implicit Play in either inline card or floating desk, on refresh or early/late schedule edges. Where new legitimate future attempts are required, offer a distinctly named `Nuova Sessione` flow scoped to a different eligible planned interval or explicitly new attempt, never reusing an ended attempt. After Stop, keep one Activity card, final actual bounds/status and original planned bounds visible; card cannot jump back to fake live state. A minimum readable-height visual projection must not falsely extend actual duration or obscure neighboring cards.

## Proposed delivery architecture and verification

1. Block visual collision and button-state regressions (pure UI projection + server-ended-attempt state); add 2- and 3-card unit/browser tests, early 09:49/09:51 before 10:00 case, short sessions, scale/mobile, historical redraw.
2. Domain + Logical + Physical overlay for *execution-protection scope* and immutable correction/retraction history before schema changes. Add PostgreSQL forward migration only if existing semantics/mappings cannot represent the required lifecycle.
3. Guard at database boundary for all relevant mutation routes (Activity replan, time popup, keyboard drag, Inspector, unschedule/remove/retire), with CAS and actor-owned errors. UI disabled affordance must use the same returned server status and explain `Esecuzione registrata — gestisci nello storico`.
4. Explicit retroactive authoring UX distinct from plan creation, using existing accepted Session manual and B10 Event Actual capabilities where sufficient; authorize correction only after its separate domain/model contract is accepted.
5. One consolidated user-local PostgreSQL/frontend/browser gate, no CI, then real-app acceptance. Never rewrite existing applied migrations or the closed Whole Logical/PM-12 baselines. Update roadmap/map/handoff and Dictionary/ORM if actual schema changes.

**Open to user confirmation:** locked scope is individual executed interval/occurrence (recommended) versus entire Activity, and handling of versioned descriptive metadata; choose before implementation. This file is a proposal, not authority to migrate or silently discard records.
