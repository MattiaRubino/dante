## 4. Temporal public API inventory governance

Temporal v1 now follows the Access/Auth principle that the public operation inventory must be mechanically enumerable and frozen.

The accepted pre-B04 baseline contains exactly 13 public Temporal operations:

```text
GET    /api/v1/temporal/timeline/window
POST   /api/v1/temporal/activities
POST   /api/v1/temporal/activities/scheduled
POST   /api/v1/temporal/activities/{activity_ref}/schedule

POST   /api/v1/temporal/events/scheduled
PUT    /api/v1/temporal/events/{event_ref}/agenda

```

The exact `(path, method) -> operationId` map is asserted in `apps/backend/tests/test_openapi_export.py`, together with exact-set equality and operationId uniqueness. This means an endpoint cannot silently disappear, appear, change method/path, duplicate an operationId or change its accepted ID without an explicit contract change.

## 5. Existing operationId compatibility policy

The 13 pre-B04 Temporal operationIds were originally generated by FastAPI naming. They are now treated as an accepted frozen v1 compatibility baseline, not as deprecated APIs.

They are deliberately not renamed merely for aesthetics because renaming would churn generated `@dante/api-client` exports and downstream imports without changing product semantics.

For every new B04+ public Temporal endpoint:

```text
route implementation
+ explicit stable semantic operationId (preferred `temporal_*` namespace)
+ exact inventory update
+ OpenAPI snapshot reconciliation
+ Orval / @dante/api-client regeneration or proven zero-diff
+ affected API/frontend tests
+ workstream documentation
```

No endpoint is added by relying only on FastAPI's implicit generated operationId.
